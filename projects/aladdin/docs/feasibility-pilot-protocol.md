# MLE-Aladdin 可行性试验方案

**方案版本：** `aladdin-feasibility-pilot-v0.1`
**状态：** 当前有效设计；不是确认性实验结果
**范围：** 一个外层 RSI 循环中的三阶段数据流程

本方案是当前研究方向的唯一实验依据。

## 1. 研究问题

在生成式任务中，数据流程能否将少量初始样本和有限人工反馈预算转化为更有效的训练数据？

```text
少量固定 seed
  -> 阶段一：数据合成（自动，不请求人工反馈）
  -> 阶段二：数据清洗（自动，不请求人工反馈）
  -> 阶段三：选择值得评审的样本并收集人工反馈
  -> 根据反馈更新合成与清洗策略
  -> 下一轮
```

人工反馈只在第三阶段进入数据流程。第一阶段负责扩充候选，不判断候选是否“好”；第二阶段执行预先固定的自动清洗，也不请求人工逐条判断。第三阶段优先选择反馈价值高、能帮助澄清要求或影响后续决策的候选。这里所说的“好”是指值得优先评审，不代表系统已判定其内容质量合格；质量和要求由反馈来判断。反馈再用于调整下一轮的合成和清洗策略。RSI 是连接三个数据操作并持续更新策略的外层循环。

现有公开数据集中的历史标签、评分和评论，与本轮新收集的人工反馈是两类数据。它们可以按协议用于固定的离线 development 评价或隐藏标签回放，但阶段一、二不会将它们当作逐条反馈输入生成器或清洗器。最终的盲测人工评价也独立于更新循环，评价结果不回流到当前实验策略。

首轮研究检验可行性和作用机制。不能用历史标签声称节省了真实人工时间。要支持该结论，必须开展真人试验，评审新生成的候选并记录耗时。

## 2. 数据集决策

### 主要数据集：PRISM

完成数据访问、提供方条款、隐私和 PII 检查后，用 PRISM 开展主要的人工反馈研究。

- 来源：`HannahRoseKirk/prism-alignment`。
- Manifest 固定版本：`18ab5cfb37456f4ec8cbc00212ce54cf7b1239f6`。
- 在许可允许的范围内，保留参与者、对话、轮次、候选回答、评分、选择属性和开放式反馈之间的关系。
- 按 `user_id` 划分，同一参与者的全部对话和轮次放在同一角色中，避免一个人的偏好同时进入 seed、feedback、development 和 final-test。
- 本轮真人反馈尚未开始时，历史评分和评论不得当作新收集的反馈。它们只可用于预先指定的离线 development 评价，或在阶段三的单独回放实验中按查询选择结果释放。

PRISM 与目标场景较接近：样本有限，数据带用户关联，包含候选回复和可以逐渐澄清需求的人类反馈。但单靠该数据集不能证明新的人力时间节省。

### 受控数据集：HelpSteer2

HelpSteer2 用作受控反馈回放和评价器校准，不作为主要的用户适配基准。

- 来源：`nvidia/HelpSteer2`。
- Manifest 固定版本：`990b2711a36180dd19d9c94b8627844866f8982a`。
- 保留五个原始评分：helpfulness、correctness、coherence、complexity 和 verbosity。
- 同一 prompt 的回答作为一组。官方 validation 保持封存。
- 可以按明确声明的规则把分数转为成对偏好，但原始分数和并列关系必须保留，供审计使用。

HelpSteer2 可以在较干净且可重复的标签回放条件下检验反馈选择机制，但没有持续的用户身份信息，因此不能据此声称学会了某一个用户逐渐变化的要求。

首轮 HelpSteer2 回放使用 `helpfulness` 作为偏好目标：较高分胜出，同分视为平局。其他四个维度分别报告。不能不加说明地把五维分数平均成一个标签。之后若做多属性实验，须预先登记聚合规则和平局阈值。

### 暂缓数据集：CoAuthor

首轮试验不纳入 CoAuthor。它可用于外部写作和编辑演示，但接受、拒绝和后续修改不自动构成偏好标签。模型训练或再分发前，须向维护方确认数据使用条款。待 PRISM/HelpSteer2 可行性检查通过后再考虑增加。

## 3. 任务单位与数据划分

任务单位是一条输入和一个或多个候选 assistant 输出。训练记录包含：

```text
任务输入 + 可用上下文 + 候选输出；第三阶段反馈产生后，才关联反馈状态
```

初始 seed 包含预先固定数量的 source group。生成器从固定 seed 补充候选，清洗器按冻结规则自动处理；经过清洗的候选进入待选池。只有第三阶段选中查询后才收集人工反馈。

| 数据角色 | 用途 | 策略决策期间能看到的标签 |
|---|---|---|
| Seed | 初始样本及提示词/上下文示范 | 仅 seed 标签 |
| Feedback pool | 查询选择的候选池 | 查询获选前隐藏反馈标签 |
| Development | 调整阈值和检查失败模式 | 仅可用于试验开发 |
| Final test | 一次性、仅报告的最终评价 | 正式最终运行前不可见 |

分组分配由记录下来的 split seed 确定。对 PRISM，group 是参与者 `user_id`；其全部 `conversation_id` 都随参与者进入同一个角色。合成/编辑样本继承 parent 的 source group。合成、清洗、选择、阈值调整和策略更新过程均不得加载 final-test 数据。

首轮试验按用户划分为 seed 20%、feedback pool 40%、development 20%、final test 20%，并通过 manifest 审计。如果可用 PRISM 子集无法支持这些比例，应缩小试验规模，不能把 final-test group 移入反馈池。

## 4. 固定的阶段对照

可行性试验不对所有数据操作做全因子组合。先在相同候选池上比较各阶段方法，再把选出的实用配置用于系统比较。

### 阶段一：数据合成

实验一数据合成对照的生成模型与下游任务模型统一固定为 `Qwen/Qwen3-8B`，checkpoint revision 为 `b968826d9c46dd6066d109eabc6255188de91218`。正式 runner 会校验模型 ID 与 revision；服务器生成 API 必须明确以该 revision 启动。生成 API 和训练 chat template 均关闭 thinking 模式。替换模型需要先修改并重新冻结实验协议，不能在同一矩阵中混用。

1. **Seed-only：** 不生成新记录；所有实验组使用相同 seed group。
2. **固定提示词合成：** 使用相同 seed、生成模型、候选数量、解码设置和 token 预算。比较前冻结提示词，且不能读取后续轮次反馈。
3. **改造版 Self-Instruct：** 使用已发表的 seed 驱动流程，从相同 seed 生成新的任务输入/回答记录。与固定提示词组使用相同生成预算和输出格式。对 PRISM 而言，这是从 instruction 生成改造为对话回答生成，须记录接口改造，不称为直接复现 Self-Instruct。
4. **改造版 Evol-Instruct：** 仅在确认性组件比较中纳入。使用已发表的复杂度增加操作演化任务指令或任务属性，再生成对应回答。只适用于可表示为 instruction/task generation 的任务。这是适配版，不是直接复现 response generation，并须匹配生成预算。首轮暂不使用 Magpie，因为其依赖模型/模板的设置不同，当前结果不需要引入这种比较。

阶段一只做必要的 JSON/schema 检查和文本规范化，不请求人工反馈、不做语义质量判断或按人工意见筛选候选。数据合成方法对照可以在生成和训练完成后读取固定 development 标签计算结果指标；这属于离线结果评价，不是反馈查询，也不会把单条标签释放给生成器。PRISM seed 中预先存在的历史选择结果属于固定初始数据，不是本轮交互反馈。

### 阶段二：数据清洗

在完全相同的合成候选池上比较：

1. **不清洗：** 解析通过的候选全部保留。
2. **确定性清洗：** 删除格式错误、空输出、规范化后的精确重复，以及按冻结的字符 5-gram TF-IDF cosine 阈值 `0.92` 判定的近重复。
3. **固定模型评分过滤（可选）：** 在确定性清洗后调用冻结版本的自动 judge，并按预先固定阈值过滤。judge 分数是自动代理信号，不是真值；阶段二不使用新的人类标注来校准阈值或逐条审查清洗结果。若没有可预先冻结且可复现的 judge，此组不进入主比较。

质量 judge 必须与任务模型分开，并固定模型版本、提示词、解码设置和调用成本。阶段二报告保留率、重复率、覆盖变化、处理成本及固定 development 集上的下游结果；没有独立人工标签时，不报告“误删率”或“低质量残留率”，也不把 judge 分数解释为客观质量。对 judge 清洗器的人工抽查只能放在第三阶段的反馈预算中，并计入相同人工预算；未实现这套协议前，主实验只比较不清洗和确定性清洗。

### 阶段三：反馈选择与标注

第三阶段是本流程唯一主动请求新人工反馈的阶段。反馈选择方法使用相同候选池和累计反馈预算，优先挑出值得请人判断的样本；选中后再展示候选并收集判断：

1. **随机选择：** 从 group 中均匀抽样并记录随机种子。
2. **偏好不确定性：** 用冻结偏好模型对同输入的候选比较按不确定性排序，是基于文献的主动偏好学习基线。
3. **分歧诊断：** 按冻结 judge 提示词或 requirement 假设间的分歧排序。排序时不暴露隐藏人工标签。
4. **单位评审成本影响力（拟议方法）：** 按预期下游影响除以预计评审时间排序。

候选组 `q` 的拟议分数为：

```text
score(q) = preference_uncertainty(q) * affected_pool_count(q)
           / max(predicted_review_seconds(q), 1)
```

`affected_pool_count` 必须在释放反馈标签前估算：它表示同一冻结任务/需求 cluster 中，有多少待处理候选可能因为该反馈而改变合成或清洗决策。偏好不确定性在 development 反馈上校准，并在选择前冻结。评审时间预测来自试验前的小型计时校准，不能使用当前隐藏标签更新。平分时按共同随机种子打破。

首轮主比较暂不纳入 diversity/core-set。只有 PRISM 任务表示和 embedding 空间稳定、且预算允许相同查询数量时，才把它作为次要实验组。

### 真人反馈协议

标注单位是一条新合成的训练记录，展示其任务输入、必要上下文和候选输出。评审者回答：

1. **可用性：** `usable`、`needs_revision`、`unusable`、`cannot_judge`。
2. **主要原因：** 从冻结标签中选择一个或多个，例如 `incorrect`、`irrelevant`、`incomplete`、`unclear`、`format`、`style`、`repetitive`、`other`。
3. **需求清晰度：** `clear`、`partly_unclear`、`unclear`。
4. **可选修改：** 简短修改或说明建议。不能强迫每次判断都写长解释。

两个或多个候选拥有同一任务输入时，另行进行盲测成对比较：`A preferred`、`B preferred`、`both acceptable`、`neither acceptable` 或 `cannot judge`。随机化左右顺序。不能把不同输入的回答当成一对偏好比较。

展示当前已确认的要求和足以判断样本的上下文，不展示生成方法、选择分数或实验组别。允许选择 `cannot_judge` 和 `unclear`，不要强迫评审者虚构偏好。修改建议可以不填；若建议揭示新要求，应显式记录，不能默默推断。

每个 annotation event 记录假名化 annotator ID、record/source group ID、任务输入、展示的回答、判断、原因标签、可选修改、需求清晰度、实验组、轮次、随机显示顺序、开始/结束时间戳及是否请求澄清。阅读、判断、编辑和澄清时间都计入人工预算；只有按预先声明的超时规则才可排除闲置时间。敏感原始反馈放在公开仓库之外，并遵守数据隐私及保留规则。

对于 synthesis RSI 对照，策略更新必须可审计。记录反馈事件、对合成指令或示范集的拟议修改、修改理由、产生的新策略版本，以及该版本生成的下一轮记录。确定性更新可以把人工确认可用的样本作为示范、把确认过的修改建议作为目标、把明确表达的新要求加入生成约束。不能只因为某样本被标成 `unusable` 就把它当负训练目标。LLM 生成的反馈总结只能作为建议，须经评审者确认才生效，确认耗时也计入人工预算。

正式试验前，用一组不在评价池中的校准样本培训标注者。随机插入少量重复题，估计同一标注者的一致性。报告一致率及 `cannot_judge` 比例，不能静默删除分歧。先对标注表单做小试，估计评审时间中位数，再确定固定人工分钟预算和样本量。不能在没有计时/统计功效试验前随意指定样本量。

项目负责人可以先标少量样本，检查说明和界面是否清楚，但这些只能作为可用性试验数据，不是主要结果的独立证据。若要作一般性结论，应招募目标任务人群中的独立标注者，并对评价样本进行多次独立判断。正式标注前冻结 rubric，对实验组盲测并随机化样本顺序，报告标注者间一致性、分歧和置信区间。不能把相互矛盾的判断强行压成所谓“客观”单标签。

如果研究的是某个具体用户的个性化需求，该用户反馈本身就是目标，而不是小组多数票。要按用户分别保留反馈和评价，并将结论限定为用户特定结果，不推广到其他用户。若研究群体数据质量或平均偏好，则要使用多个独立目标用户/标注者，并在用户层面分析。两种情况下，都要将公开数据集回放与新收集的真人反馈作为不同证据来源报告。

历史回放只能释放真正对应被选中 group 的反馈字段。对 PRISM，若存在明确的选择信息或候选级评分，可使用它；不能将对话级评论复制成每个 response 的标签，也不能给两个无关 response 伪造 pairwise label。若 PRISM 样本没有可信的候选级反馈，就从反馈回放中排除，只保留在描述性数据审计中。历史回放不能代替上述真人标注协议。

## 5. 按阶段依次开展组件实验

实验一次推进一个阶段；后续阶段使用前一阶段选定的配置。final test 始终封存。下文四组系统实验是最后的集成试验，不是第一项实验。

### 实验一：选择合成方法

#### 数据合成方法对照

先比较不递归更新的合成方法：

- `S0 Seed-only`：只保留初始 seed。
- `S1 Fixed-prompt synthesis`：使用冻结提示词，从相同 seed 生成候选，并匹配生成预算。
- `S2 Adapted Self-Instruct`：用已发表的 seed 驱动方法，在相同输出格式和预算下生成样本。
- `S3 Adapted Evol-Instruct`：任务兼容且实现版本可固定时，在确认性比较中纳入。

所有实验组使用相同的必要解析和文本规范化。本实验不使用语义质量清洗、反馈选择或递归策略更新。生成方法使用相同的服务端总 token 预算，实际生成候选数作为产出指标报告；下游任务模型使用相同训练样本数和实际输入 token 预算。默认 256 个训练槽位中，`S0` 全部来自 seed，`S1/S2` 各用 128 个 seed 槽位和 128 个合成槽位；候选不足时只在相应来源槽位内重复，并在 manifest 中披露重复率。

当前可复现的 development 代理评价使用 PRISM 的 `if_chosen` 标签：从 development 用户组按固定种子 101 抽取 64 组；对每个 source group/conversation/interaction，计算 task model 对 chosen 与 rejected 回答的条件平均 log-probability，并报告有效 chosen-rejected 配对上的排序准确率；同时报告 development 回答平均 NLL。所有策略和训练随机种子使用相同 development 用户组。它用于数据合成方法的可行性筛选，不等同于盲测真人偏好。只有当某种合成方式在可接受生成成本下改善预先指定的 development 指标并带来有效的新覆盖时，才选为后续配置。如果合成方法只制造重复样本或没有提升指标，就保留 `S0`，并记录该任务上合成没有价值。选定后，冻结方法、提示词/流程、模型版本、解码参数和生成 token 预算。

可行性运行先比较 `S0`-`S2`。在作出确认性合成结论前，若任务兼容且实现可固定，再加入 `S3`。预算匹配下 development 表现最好的非递归方法成为后续 RSI 对照的固定合成 baseline。

该静态比较只用于选择 baseline，本身不能证明 RSI。

#### 合成策略递归更新对照

取数据合成方法对照选定的固定合成方法，使用同一预声明的基础清洗器（schema 校验、规范化、精确去重）和同一反馈预算，至少运行两轮。此处不引入数据清洗方法比较中的语义清洗器。三组使用相同新增候选数、相同人工反馈条数（或相同实测人工分钟）。各组选择到的反馈都作为下游训练监督；只有更新组能修改下一轮合成策略。比较：

- `R0 Fixed`：合成提示词/流程保持不变；反馈作为与其他组相同的下游监督，但不能修改提示词、示范或样本分配。
- `R1 Random-update`：随机选择反馈，并据此更新合成策略。
- `R2 Aladdin-update`：按单位评审成本影响力选择反馈，再用释放的反馈更新合成策略。

`R0`-`R2` 的清洗器、任务模型、候选数、训练 token 预算和反馈预算都必须相同。这样才能检验反馈驱动的合成变化是否逐轮带来改善。逐轮报告质量和覆盖、合成策略版本、反馈成本，以及是否真正触发策略变化。

`R0` 是非递归对照；`R1` 检验反馈更新本身是否有用；`R2` 检验拟议的反馈选择是否改进更新效果。这里是首次直接检验合成阶段 RSI 的实验；还需要最终四组实验验证完整的合成-清洗-选择流程。

若要声称人工反馈改进合成，递归更新对照必须使用真人对新生成候选的评审。PRISM/HelpSteer2 历史标签可以用于独立的选择策略回放，但不能给新合成候选贴标签，也不能证明这一 RSI 主张。若暂时不能进行真人标注，只能将该对照报告为方案/机制模拟，不得声称真人反馈改善了合成。

每轮都使用冻结且按 group 隔离的 development 评价集，盲测当前轮训练模型与上一轮/固定控制模型的成对偏好。final test 保持封存。只有在不超过共同生成、训练和人工时间预算的前提下，预先声明的主要 development 指标提升，才算该轮改善；候选样本本身的质量提高不够。

### 实验二：选择清洗方法

用实验一冻结的结果生成一个共同候选池，比较：

- `C0 No-cleaning`；
- `C1 Deterministic-cleaning`；
- `C2 Frozen-model-quality-cleaning`，可选自动 judge 对照，不使用本轮人工标签校准。

固定下游任务模型、训练 token 预算和候选预算。根据固定 development 集下游表现、保留率、重复率、覆盖变化和处理成本选择清洗器。没有独立人工真值时，不报告误删率或低质量残留率。进入反馈选择实验前冻结最终清洗器和所有阈值。

### 实验三：选择反馈策略

使用已冻结的合成与清洗方法构造一个反馈池，在相同反馈预算下比较 `Q0 Random`、`Q1 Preference-uncertainty` 和 `Q2 Impact-per-review-cost`。预算允许时，将分歧作为诊断组。先做隐藏标签的历史回放以检查选择机制，再对新候选开展一批真人标注以测量实际耗时。不能用回放结果声称人工时间下降。

### 实验四：集成选定组件

实验一至三冻结后，再开展下一节的四组系统对照。该实验检验所选组件能否作为递归数据流程共同工作，不能取代三个组件实验。

递归比较还必须包含“固定合成 + 随机反馈”控制。否则提升可能来自更强的合成 baseline，而不是反馈选择或递归更新。

## 6. 系统对照

组件试验后，运行四组系统对照。任务模型、候选数、训练 token、计算量和累计人工分钟预算相同：

| 组别 | 合成/清洗 | 反馈策略 | 是否更新下一轮 |
|---|---|---|---|
| A. Seed-only | 不合成、不清洗 | 无 | 否 |
| B. 固定流程 | 选定的非递归合成 + 选定清洗器 | 随机回放/真人查询 | 否 |
| C. 随机反馈 RSI | 与 B 相同的初始流程 | 随机查询 | 是，同时更新合成和清洗 |
| D. 拟议 RSI | 与 B 相同的初始流程 | 单位评审成本影响力 | 是，同时更新合成和清洗 |

主要比较：

- `B - A`：固定数据流程是否比少量 seed 更有帮助。
- `C - B`：随机选择反馈时，递归更新是否有帮助。
- `D - C`：相同递归流程中，拟议反馈选择策略是否有帮助。

可行性试验稳定后，再增加两个机制消融：仅更新合成、仅更新清洗。在这些消融前，不要声称反馈分别改善了两个操作。

## 7. 轮次安排与预算

可行性试验包含两个更新轮次。历史回放下每组每轮 16 次反馈比较；真人试验采用相同的最大比较次数。回放诊断使用三个策略随机种子；真人计时试验先进行两批独立计时标注。

所有实验组保持以下预算一致：

- seed group；每个合成方法使用共同 token 预算，实际候选数单独报告；
- 任务模型 checkpoint 和训练 token 数；
- 质量 judge 预算和提示词；
- 最大反馈比较数和最大人工分钟数；
- development 与 final-test 评价集。

首次确认性运行前，精确模型版本、解码参数、GPU 型号和运行时版本必须写入 manifest。可行性运行可用于发现工程问题，不能只挑选性报告有利结果。

## 8. 评价方式

### 主要结果

在封存的 final-test 新输入上进行盲测人工成对偏好评价。统计目标是预先声明目标人群的偏好，不是普遍客观质量分数。收集测试判断前冻结问题和 rubric。随机化回答顺序，隐藏系统身份，并允许 `tie/both acceptable`、`neither acceptable` 和 `cannot judge`。

若要对某个用户群体作结论，应从该群体招募独立评价者。每个 test 条目由多名评价者独立判断；样本量和评价人数通过计时/功效试验确定，不能看完结果再决定。条件允许时，final evaluator 与提供系统更新反馈的人分开。若无法分开，须披露，并保证用户/任务隔离。

报告胜率和平局及其置信区间，处理同一任务/用户和标注者的重复评分。报告原始一致率，以及适合标签类型的机会校正一致性指标，例如 nominal 类别用 Krippendorff's alpha，ordinal 评分用 weighted kappa。保留分歧和 `cannot_judge`，不要静默合并为单一标签。高一致性支持测量一致，不代表普遍正确。

将可验证条件（例如格式要求或有参考依据的事实）与偏好条件（例如语气、风格和有用性）分开，并分别报告。论文结论必须匹配评价者人群范围：单个用户的判断只支持用户特定结论；抽样面板只支持其所代表的人群和任务范围。两者都不能被称为客观 ground truth。

不能用 final-test 判断选择方法、调提示词、改 rubric 或更新策略。若同一人既写需求又评价最终输出，须记录其双重角色。

### 阶段诊断指标

- 合成：独特率、任务/需求覆盖和候选生成成本。
- 清洗：保留率、重复率、覆盖变化、judge 成本和固定 development 集下游表现；若未来在第三阶段预算内专门审查清洗决定，才额外报告人工审计指标。
- 反馈选择：每分钟有效反馈数、实际评审秒数、由反馈触发的策略变化次数，以及相同累计人工分钟下的下游质量。
- 全流程：逐轮质量、训练/生成/judge/人工成本，以及每次更新后的准确策略版本。

回放中要预先定义反馈的“有效性”，例如释放的标签改变 requirement state、清洗决策、合成分配或下游训练记录。回放的有效性和标签恢复准确率是机制指标，不代表真实人工耗时。

## 9. 执行顺序

1. 固定数据集版本、许可/使用条款、模型版本和 split manifest，完成 PII 与泄漏审计。
2. 在 development pool 上运行合成组件比较。
3. 在同一候选池上比较自动清洗方法；不在阶段二安排人工标注。
4. 在阶段三用隐藏标签回放检查随机、不确定性偏好和单位评审成本影响力策略；分歧作为诊断。
5. 阶段三对新合成候选开展真人标注/计时研究，比较相同人工分钟预算下的反馈效用。
6. 在等预算下运行四组递归系统对照，只有反馈选择和更新组在第三阶段接收人工反馈。
7. 冻结确认性协议后，独立开展一次盲测 final-test 评价；评价结果不回流到系统更新。

当前交付物是试验方案和 manifest 设计。
