# Model Framework 绘制思路

## 目标

绘制一张端到端总框架图，让读者快速看懂：Data System 如何持续处理数据、从运行中获得证据、提出系统修改、验证候选修改，并将有效更新用于后续运行。图需要同时体现数据操作和长周期稳定性。

## 论文图的组织方式

### G-Designer：分阶段展开

[G-Designer](https://arxiv.org/abs/2410.11782) 第 4 页 Figure 3 将框架按 Materials、Construct、Design、Optimize 分成连续阶段。每一阶段使用独立区域，区域内部再展示输入对象、处理模块和输出；跨阶段用箭头表示信息传递。

可借鉴之处：先按阶段划分总图，再在阶段内展开关键模块，避免把所有组件挤在同一层。不要照搬其多智能体通信拓扑或节点内容。

### EvoFlow：展示候选演化闭环

[EvoFlow](https://arxiv.org/abs/2502.07373) 第 4 页 Figure 1 展示工作流的组成和搜索过程；第 8 页展示不同方法得到的工作流结构。它把工作流作为可变对象，并呈现候选产生、变化和选择之间的关系。

可借鉴之处：把 Data Harness / 数据策略画成明确的可改进对象，并区分稳定版本与候选版本。不要把 LEGO 画成 EvoFlow 的种群进化算法，除非后续实验确实采用该算法。

### G-Memory：展示经验层级和检索更新

[G-Memory](https://arxiv.org/abs/2506.07398) 第 2 页 Figure 1 和第 5 页 Figure 2 展示 Insight、Query、Interaction 三层记忆，以及任务到来时的检索和任务完成后的更新。

可借鉴之处：将 Memory / Skill 的来源、适用条件、运行证据和状态变化画出来，使经验治理不是一个无内容的“Memory”方框。LEGO 的经验结构应按自己的数据处理场景定义，不直接复制其三层图结构。

### MemEvolve：区分经验内容与记忆机制

[MemEvolve](https://arxiv.org/abs/2512.18746) 第 2 页 Figure 1 展示记忆系统如何编码、存储、检索和管理经验，并把经验演化与记忆架构演化分开表达。

可借鉴之处：在图上区分“被保存的数据处理经验”和“经验的管理 / 使用规则”。这有助于说明 T2 治理的是经验与 Skill 的生命周期及适用性，不只是增加记忆条目。

### HarnessForge：展示 Harness 与执行策略的关系

[HarnessForge](https://arxiv.org/abs/2606.01779) 第 3 页 Figure 1 展示 Harness 与 Policy 的适应空间及模块组成；第 8 页 Figure 4 展示多轮联合演化。

可借鉴之处：明确系统由执行结构和模型能力共同完成任务，并将模块更新放进迭代过程。MLE-LEGO 以 Data System 为整体对象、Harness 为主要改进载体；不能因此把研究范围缩窄成模型 Policy 训练。

### CoEvo-RSI：展示版本谱系和多轮更新

[CoEvo-RSI](https://arxiv.org/abs/2610.25078) 第 5 页 Figure 2 展示历史版本、诊断证据、Harness 编辑、模型继承和执行结果之间的关系。

可借鉴之处：用版本节点和谱系表达长期运行中“从哪个稳定版本提出候选、候选产生了什么结果、最后保留哪个版本”。LEGO 的版本状态和选择规则必须按自身 T1/T2/T3 设计；该图只作为谱系表达参考。

### JIT-Agent：展示 Harness 内部模块

[JIT-Agent](https://arxiv.org/abs/2608.25593) 第 2 页 Figure 1 将 Harness 拆成 Memory、Planning、Action 和 Capability，并展示不同任务对应不同 Harness 组织方式。

可借鉴之处：需要展开 Harness 时，用有语义的子模块替代一个无法解释的整体方框。MLE-LEGO 应将其映射为数据生成、筛选、清洗、训练数据选择、反馈处理、Memory / Skill 与运行控制等数据系统组件。

## 映射到 MLE-LEGO

总图建议采用左右贯通或上下分层的阶段式布局，主视觉只保留两个系统层和一个闭环。

1. **持续执行层（Action System）**：数据输入与批次 → 数据生成 → 筛选与清洗 → 训练数据构建 → Task Model 训练 / 预测 → 任务评估与运行记录。
2. **证据与状态层（Evidence Store）**：记录数据、策略、Harness、Memory / Skill、Task Model 和运行版本；保存数据质量、任务表现、成本、异常，以及反馈产生与到达时间。
3. **改进与治理层（Planning System）**：Decision LLM 根据运行证据诊断问题并提出受限修改；T2 检查经验 / Skill 的来源、适用条件和失效证据；T1 在隔离候选分支验证数据策略；T3 将延迟反馈关联到来源版本，汇总多轮表现后决定继续观察、保留稳定版本或更新版本。
4. **闭环回到执行层**：只有按预设规则通过版本决策的策略和有效经验，才进入后续批次；未通过或证据不足时，稳定流程继续运行。

## 绘制规范

- 用分区标题区分执行、证据、改进与版本决策；用箭头方向表达真实的数据流和控制流。
- 每个主要模块标出输入 / 输出或至少标出产生的记录，尤其是数据版本、策略版本和反馈来源。
- 使用颜色区分执行数据流、候选验证、经验治理、版本决策；颜色语义在图例中固定。
- 稳定版本与候选版本并排绘制，候选失败路径明确回到“稳定版本不变”。
- 反馈箭头必须指回其来源运行 / 版本，然后才进入策略决策，避免看成反馈一到就直接覆盖当前版本。
- 不使用 3D 图作为系统架构图；ExpDrawing-main 中的折线、热力图和散点图适合后续结果呈现，不适合表达模块依赖。
- 图中用状态标记区分“已有代码骨架”“待集成”“待真实运行验证”；目标架构不能暗示所有研究机制已经验证。
- 论文图只借鉴布局与信息表达，不复制论文中的实验数据、结论或专有图形。

## 图中应让读者看懂的主线

```text
数据处理与任务运行
→ 产生带版本的效果、质量、成本和反馈证据
→ 诊断数据策略或经验问题
→ 治理经验并提出候选修改
→ 隔离验证候选数据策略
→ 将延迟反馈归因到正确版本并比较多轮结果
→ 更新或保持稳定版本
→ 进入下一轮数据处理
```

图的重点不是把 T1、T2、T3 画成三个互不相干的功能框，而是展示它们如何共同限制错误传播、过时经验误用和反馈错配，从而支撑 Data System 长周期运行。
