# 研究范围与实验框架

**论文工作标题**：MLE-LEGO: Data-centric Self-Harnesses for Long-Horizon Recursive Self-Improvement

统一任务、输入输出边界、HelpSteer2 数据划分、反馈可见性和完整性条件以[长周期任务定义](long-horizon-task-definition.md)为准。本文说明研究问题、三个技术点和实验推进关系；其中待冻结的实验设计不应被视为已完成结果。

## 研究目标

MLE-LEGO 面向需要持续构建数据并更新模型的 Data-Centric RSI，研究 Data System 如何根据运行结果改进自己的整体运行方法，并在长周期中持续、安全、可恢复地执行。优化主体是 Data System 的整体状态与运行规则；Harness 是主要改进载体，同时涵盖数据构建与质量、Task Model 更新、评价、反馈、Memory、Skill、工具和运行控制。

智能体可抽象为 `Agent = Model + Harness`。在本研究中，Decision LLM 的参数保持固定；系统可持续修改的是 Data System 的运行方式、数据与模型版本，以及 Harness 中的规则、程序、经验和工具编排。单次指标上升或新增数据本身不等于 RSI 改进；更新必须能在后续任务中可靠复用，并满足预先定义的质量、完整性、成本和恢复要求。

本研究采用混合更新周期：离线建立并冻结一个可复现的初始 Data System，进入流式运行后按批次处理新输入、释放到期反馈、更新状态并继续执行。三个技术点的研究构建顺序是 T1 → T2 → T3；三者齐备后的在线调用顺序是 T3 归因反馈 → T2 管理经验 → T1 隔离候选更新 → T3 根据后续表现作出保留或恢复决定。

## 共同任务

当前首个基准是 HelpSteer2 上的 prompt-group 回答质量三分类。把同一 prompt 下的回答作为不可拆分 group，根据五个评分维度的算术平均生成 `preferred`、`rejected`、`tie` 标签。系统按批次看到当前 group 的无标签输入，先生成预测；标签按 0、2 或 5 个完整批次边界后释放。标签释放后才可进入训练和预序列评测。

HelpSteer2 没有真实用户/session 身份或天然时间顺序，评分延迟是对既有标签进行的受控回放，不是真人在线反馈，也不代表真实偏好漂移。因此，当前实验结论限于这个受控基准上的 Data System 连续运行机制。CoAuthor、PRISM 或真人反馈属于以后可注册的外部任务，不与当前 HelpSteer2 结果混合。

共同任务把系统每批的输入定义为：当前无标签 prompt groups、已到期且有来源版本的反馈、当前 Data System 版本、已验证可用的经验和剩余预算。每批输出包括：版本绑定的预测、处理后数据、Task Model checkpoint、到期反馈/待处理反馈状态、候选修改及门控/选择结果、资源消耗、完整性审计和可恢复运行状态。

## 技术一：安全自进化与故障隔离

**要解决的问题**：自进化系统需要允许提出有意义的新修改，不能把探索范围限制在固定组件白名单；但候选代码、规则、数据流程或经验更新出错时，不能破坏当前稳定 Data System 的连续运行。

**机制**：根据运行诊断提出 Data System 级候选修改；为候选建立与稳定版本隔离的数据、模型、Memory/Skill 和执行状态；检查接口、数据来源、资源边界与可恢复性，再在受控运行中验证。检查通过只表示可以进入观察，不代表长期接受。失败候选被记录并隔离，稳定版本继续处理任务；候选产生的工件不得污染稳定分支。

**端到端输入**：运行失败/退化信号、当前版本清单、候选修改、依赖和预算约束。**输出**：候选安全评估、隔离执行记录、通过/拒绝原因、故障传播与恢复结果，以及可供后续观察的候选版本。

**长周期验证**：跨连续批次注入接口错误、无效数据、超时、训练失败和部分写入等故障，测量候选隔离率、稳定流完成率、数据/checkpoint 污染、恢复成功率与耗时、重试成本。安全检查和真实故障注入是不同层次，必须分别报告。

## 技术二：可执行经验生命周期管理

**要解决的问题**：运行时间增长会积累 Memory 与 Skill；错误、冲突或条件过时的经验可能不断影响后续决策，增加检索和执行成本，最终令 Data System 退化或失控。

**机制**：每条可执行经验记录来源系统/模型/数据版本、任务条件、产生批次和验证证据。新经验先处于候选状态，经过验证后才允许检索；重复失败、上下文条件改变或与其他经验冲突时，转为待复核、暂停、冲突处理或失效状态。检索只提供条件匹配且当前有效的经验。

**端到端输入**：已归因的运行结果、诊断、候选 Memory/Skill、适用条件及历史复用成败。**输出**：经验状态转移、可检索经验集合、来源链、失效/冲突决策和相应运行成本。

**长周期验证**：随批次增长注入错误经验、过期规则和冲突 Skill，观察它们是否继续进入执行；报告经验错误复用率、验证和失效延迟、冲突残留率、检索延迟/存储增长，以及运行质量和任务连续性。

## 技术三：基于后续运行表现的更新保留与回退

**要解决的问题**：反馈可能晚到；一个版本的短期指标也可能掩盖后续退化。若反馈没有归到产生它的数据、模型和系统版本，或只凭一个批次决定保留更新，系统会发生错误晋升或反复切换。

**机制**：反馈绑定来源批次、数据版本、Task Model 和 Data System 版本；候选在多个后续可比较批次中与稳定版本并行或按冻结协议配对观察。根据预先冻结的质量、退化容忍度、稳定性与资源规则，决定接受、继续观察、保持稳定版本或恢复到已知稳定版本。延迟或未知来源反馈不能用于当前候选决策。

**端到端输入**：候选与稳定版本、版本绑定的预测、已到期反馈及成对运行记录。**输出**：可审计的反馈归因、多批次证据、保留/继续观察/拒绝/恢复决策和新的稳定版本指针。

**长周期验证**：控制反馈延迟并注入版本错配、短期噪声和真实性能退化，测量归因准确率、错误晋升率、退化暴露时长、回退正确性、恢复速度、版本切换频率和预算消耗。

## 实验推进

三个技术点共享同一初始 Data System、任务流、模型更新规则和预算口径，但各自具有对应的机制对照与长周期指标：

1. **共同任务与固定流水线**：用真实数据生成 manifest，审计 group 切分与反馈时序；运行固定流式 Task Model baseline，验证先预测后训练、parent-checkpoint 续训、状态恢复和成本记录。
2. **T1 单项机制**：先比较固定流水线 `B0-fixed` 与同流 stable branch，之后运行 `T1-shadow-clean` 和逐类故障注入 `T1-shadow-fault`，检查候选是否被隔离、稳定流是否完成及状态是否可恢复。当前代码没有可执行的“关闭隔离/关闭运行时门控”对照，不把它写成已实现消融；完整实验条件见[技术一实验协议](../experiments/technology_one/protocol-v1.md)。
3. **T2 单项机制**：固定 T1/T3，比较不保存经验、只保存文字反思和带来源/条件/验证/失效治理的可执行经验。
4. **T3 单项机制**：固定 T1/T2，比较单批次决定与预先冻结的多批次选择策略，并设置 0/2/5 延迟和反馈归因错误对照。
5. **集成与消融**：比较固定系统、各单项技术和 T1+T2+T3；在相同数据顺序、初始 checkpoint 和总预算下开展多随机种子实验与长周期故障压力测试。

表中的对照是当前实验框架。先完成 4 周期部署 smoke，再运行 10～20 周期 pilot；据此确定正式运行参数、种子数、预算、故障设置、统计终点和阈值。正式协议冻结前不解锁 `final_test`。

## 评价与结论边界

每项实验同时报告四类结果：

- **任务与数据质量**：各批次和最终阶段的 accuracy、macro-F1、分类别表现、数据有效率和来源完整率。
- **运行稳定性**：计划批次完成率、未恢复中断、候选故障隔离率、checkpoint 连续性、恢复成功率/耗时及退化暴露时长。
- **反馈与版本治理**：泄漏违规、反馈归因准确率、错误经验复用、错误晋升、无效回退和版本切换频率。
- **资源成本**：Task Model 训练和预测时间、Decision LLM 调用（如该实验使用）、存储/检索开销、失败尝试与恢复成本、预算超限。

任务质量提升不能替代稳定性证据；进程完成也不能证明更新有效。HelpSteer2 受控回放不能支持真人偏好、真实在线交互、自然时间漂移或完整 Data-Centric RSI 部署效果的结论。所有主张须绑定对应协议、运行工件和可复核证据。

## 研究依据

[ReAct](https://arxiv.org/abs/2210.03629) 提供根据观察在推理与行动间交替的思路；[Reflexion](https://arxiv.org/abs/2303.11366) 研究把反馈转成后续可用的文字经验；Self-Harness 表示将 Harness 作为持续改进对象的一类研究思路，本项目并不把该术语限定为某一篇文章的专有定义。[DataEvolver](https://arxiv.org/abs/2606.07001) 等工作研究数据处理操作或流程的自动改进。

MLE-LEGO 的研究问题聚焦于持续运行中的系统级安全、经验治理、延迟反馈归因和更新保留。这些技术点是待实现、待比较、待验证的研究假设；是否具有方法优势或新颖性，需要在完成相关工作核查及正式实验后再作判断。
