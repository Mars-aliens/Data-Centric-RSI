**论文标题**：MLE-LEGO: Data-centric  Self-Harnesses for Long-Horizon Recursive Self-Improvement

**研究主题**

MLE-LEGO 面向需要持续开展数据构建与模型更新的 Data-Centric RSI，研究支撑数据处理的 Harness 如何根据运行结果改进自身。这里的 Data Harness 负责组织数据合成、增强、选择和清洗，决定何时调用工具、请求人工反馈，以及如何使用过去的实验经验。随着任务持续运行，这些组织方式也应当可以调整，使系统不仅得到更好的数据，还逐步形成更有效的数据改进方法。

这一问题的难点在于，各个改进对象相互影响。生成策略决定候选数据的内容，筛选规则决定哪些样本进入训练，训练结果影响下一次的数据构建方向，而 Memory 与 Skill 又会影响后续的方法选择。因此，某个组件单独改善，并不一定带来整体提升。例如，更新生成策略后，如果筛选规则仍沿用旧要求，新生成的有效样本可能无法被保留。系统需要判断哪些组件应当一起修改，并通过实际运行检查这些修改是否配合有效。

MLE-LEGO 围绕执行、反思、修改和验证建立自改进过程。系统首先根据数据处理记录、训练结果和人工反馈，找出需要调整的步骤，再结合组件之间的依赖关系，提出范围明确的修改。修改可以涉及操作顺序、生成与筛选规则、工具调用方式，也可以涉及经验检索和 Skill 的实现。候选修改经过实际实验后，有效部分被保留到后续使用的 Harness 中，相关结果也成为下一次选择修改方法的经验。这样，反馈能够转化为可执行的变化，而不只是形成一段事后总结。

长程运行要求系统进一步考虑修改的后续作用。随着数据积累和任务模型更新，原先有效的方法可能逐渐失效，而新策略的价值也可能需要经过多次数据构建和训练才能体现。人工意见和训练结果还可能延迟返回，因此必须关联到当时使用的数据、模型和 Harness，避免将旧方案的反馈错误地用于评价新方案。框架由此需要比较修改前后的连续运行表现，判断一次更新是否既改善当前任务，也有助于后续数据构建。因此，MLE-LEGO 的核心研究问题是，如何将相互依赖的数据处理组件组织成可持续优化的整体，并让系统从实验中学会修改这个整体。论文重点检验，依赖关系引导的组合修改，以及基于后续实验效果的更新选择，能否比固定流程、仅保存反思经验或逐组件修改，更有效地支持长程 Data-Centric RSI。

**研究动机与方法依据**

[ReAct](https://arxiv.org/abs/2210.03629) 将推理与操作结合，使智能体能够根据当前观察选择行动，并利用执行结果调整下一步决策。在此基础上，[Reflexion](https://arxiv.org/abs/2303.11366) 将任务反馈整理为可保留的反思经验，帮助智能体改进后续尝试。[Self-Harness](https://arxiv.org/abs/2606.09498) 进一步将支撑智能体运行的 Harness 作为改进对象，根据执行中发现的问题提出修改，并通过实验验证后保留。这些工作提供了从交互决策、经验积累到运行方法自我修改的研究基础。

MLE-LEGO 将 Self-harness 思路（不特指上面那篇文章，而是 harness 自进化这个思路的统称）用于 RSI 的 Data System，重点研究多个相互依赖的数据处理组件如何共同改进。数据生成方式的变化会影响候选样本的内容，筛选规则会影响实际进入训练的数据，而训练结果又会改变下一次生成策略和经验选择。反思文字可以帮助调整决策，但未必能同步改变相关程序与执行规则。直接改写整个流程，则容易同时改变过多内容，使系统难以判断哪些修改有效，以及哪些修改引入了新的问题。

因此，本工作采用**执行、反思、修改、验证**的持续改进过程。系统根据实际运行反馈，结合数据处理步骤之间的依赖关系，提出针对单个组件或相关组件组合的修改，再在一致的实验条件下比较修改前后的效果。验证不仅检查当前批次是否改善，也关注更新后的 Harness 在后续数据构建与模型训练中是否继续有效。通过验证的修改进入后续执行，其适用条件和运行结果同时用于指导下一次改进。

这一过程可以在负责决策与修改的 LLM 参数保持固定的条件下开展。持续更新的是实际执行的流程、规则、Skill，以及经验的保存和使用方式。学习结果由此体现为系统运行方法的改变，并通过后续实验不断检验和修正，从而形成面向数据 Harness 的递归自我改进。

**需要优化的 Harness 是什么**

我们工作中的 Harness 特指服务于 Data System 的运行组织机制，包括数据处理的执行顺序与条件、各步骤使用的程序和 Prompt、工具选择与人工反馈规则，以及 Memory 和 Skill 的使用方式。它决定系统如何构建数据、利用反馈并开展后续实验。数据样本、模型检查点和待返回的反馈属于运行过程中产生和使用的信息，新增这些内容本身并不代表 Harness 得到改进。Harness 改进需要改变后续仍会使用的处理方法、执行规则或经验使用方式。

为支持有针对性的修改，系统需要明确每个处理步骤接收什么输入、产生什么输出，以及使用哪些程序、规则和经验。同时，运行记录保留数据处理、模型训练和结果评价所对应的版本，使反馈能够关联到当时实际采用的方法。这样，当某次实验效果不佳时，系统可以检查相关步骤，并判断需要调整一个组件，还是同时修改多个相互影响的组件。

[DataEvolver](https://arxiv.org/abs/2606.07001) 已研究数据处理操作与整体流程的自动改进。而我们进一步关注长程运行中，如何根据持续返回的反馈选择修改对象、协调相关组件的更新，并通过后续数据构建和模型训练检验修改是否有效。研究重点是让 Harness 逐步形成更有效的数据改进方法，而不仅是完成一次流程调整。

**核心pipeline**

**执行当前 Harness → 比较预期与实际结果 → 提出相关组件的修改 → 运行候选版本 → 保留有效修改与适用经验 → 继续数据实验。**

执行阶段采用 ReAct 式工具交互（最好在它基础上有所优化），完成数据处理、训练提交和结果读取。反思阶段针对已经返回的结果，形成一条简短记录，说明出现了什么问题、哪些组件可能有关、拟修改什么，以及希望看到什么变化。没有实际结果的猜测不能直接变成长期规则。修改阶段将反思转成程序、Prompt、流程或经验使用方式的候选变化。验证通过后，变化写入下一次实际执行的 Harness。失败修改同样记录适用条件与结果，以减少重复尝试。这里持续学习的是可执行的方法，而非单纯延长上下文。

**技术一：根据依赖关系提出成组修改**

系统从出问题的数据或模型结果回查实际使用的操作，选择最相关的局部区域。它同时检查上游输入和下游使用要求，避免只改一个组件却破坏整个流程。

候选可以修改生成提示及其筛选规则，也可以修改某个 Skill 和对应的调用条件。每次限制修改规模，先尝试相关组件的小组合，只有失败后才扩大范围。修改对象包括操作替换、分支调整、Prompt 修订、程序修改和 Memory 检索规则修改，不预设必须训练模型参数。

为检查成组修改是否必要，在预算内保留单项修改作为对照。组合优于各单项时，才说明这些修改可能需要配合。版本关联只帮助定位，不能直接证明某个组件造成了错误，结论仍来自对照执行。

这部分技术要检验的是，相同候选数量和执行预算下，依赖关系是否帮助系统找到更有效的修改，而不是图结构是否画得更复杂。

**技术二：让反思经验转化为可复用的修改方法**

保留的经验记录当前问题、适用的数据与模型条件、实际修改和验证结果。下一次遇到相近情况时，系统检索相应修改方法，先检查条件是否匹配，再生成当前任务的候选。

经验中的通用判断与具体数值配置分别保存。成功修改不能被直接推广到所有数据。反复失败的方法降低检索优先级，数据或模型条件改变时重新验证。重复操作可以整理为 Skill，但需要实际执行检查，而不只是生成一段自然语言说明。

这一机制继承 Reflexion 的反馈学习思想，同时将学习结果落到 Harness 的执行结构。它也需要与仅追加反思文本的方法比较，检验可执行修改是否比更多经验文字更有效。

**技术三：使用连续运行结果选择修改，并处理晚到反馈**

每次比较从同一数据、模型和经验起点创建当前版本与候选版本。先做可执行检查，再按相同预算运行若干开发批次，让数据生成、模型更新和经验积累在各自分支内继续进行。不同分支不共享新产生的经验或模型。

候选选择同时考虑多批次平均表现、仍然适用的历史任务表现和总成本。初始实现可以用 3 个开发批次检查后续影响，并用只检查 1 个批次的版本作为对照。这些批次只能来自当时可用的开发数据，不能提前使用未来真实任务或最终测试。

人工意见与训练结果按原运行版本返回。晚到反馈可以要求重新检查已采用修改，但不能被记作当前新版本的成绩。效果不明确时保持当前方法，发生退步时恢复相配套的 Harness、数据清单、经验与模型检查点。原始人工记录保留。

[HarnessEvolve](https://arxiv.org/abs/2609.00829) 已采用当前与近期任务检查来选择更新。这里进一步检查修改引起的后续数据构建和模型学习结果，而不只重复评价已有任务。短程分支运行只能帮助估计后续收益，仍需在完整长程任务中验证。

**数据从哪里来**

目前核对的公开数据并不直接提供一套包含持续 Harness 更新及完整人类反馈的长程 Data-Centric RSI 记录。可以使用真实任务与反馈构建实验流，但需要明确哪些是原始记录，哪些是研究中安排的运行条件。

首个可重复设置使用 [HelpSteer2-Preference](https://huggingface.co/datasets/nvidia/HelpSteer2) 的生成任务子集，保留原始输入、候选和人工理由，用于控制反馈预算和比较数据筛选。更接近自然写作的设置使用 [CoAuthor](https://coauthor.stanford.edu/) 的完整写作会话，保留编辑与交互顺序。需要用户差异时，再使用 [PRISM](https://huggingface.co/datasets/HannahRoseKirk/prism-alignment) 的用户与会话关系。

每个任务保留少量初始案例，后续输入分批到来。原始任务或会话先整体划分，所有增强跟随其来源。写作中的拒绝不是确定负标签。不同用户的数据也不能直接拼成同一人的稳定偏好。

**如何构建长程实验环境**

以数据较充足的任务组为例，先给出 10 条种子案例，再依次开放 20 批、每批 50 条真实任务输入。这是一组可调整的初始实验参数，需要按实际子集规模确定。样本不足时缩短序列，不重复测试数据凑长程。

在固定总预算下，让 Harness 自行安排合成、增强、选择和清洗，并选择需要揭示的历史反馈。未请求或尚未返回的偏好方向、理由和修订结果全部隐藏。分别设置即时返回，以及延迟 2 或 5 批返回的反馈，检查系统是否能够利用晚到信息。数据分批和延迟是人为控制的实验条件，不描述成真实部署历史。

稳定任务流作为基础设置。需要研究任务变化时，按预先公开的顺序改变任务类型或内容比例，同时保留仍适用的旧任务检查。仅更换文体不能被解释为某个人真实改变了偏好。

历史反馈只能返回给原有候选，不能直接评价新生成内容。早期开发可以使用独立人工反馈训练或校准的模拟评价器，使真实模型训练能够持续运行，但结果明确记为模拟环境表现。最终选择部分代表性任务，新增真人反馈检验实际效果。模拟评价器及候选选择程序均不读取最终人工测试反馈。

**具体 Baseline 设置**

所有方法使用相同的决策 LLM、初始任务模型、数据工具、输入序列和总预算，具有相同的原始记录访问权限与上下文长度限制。下游模型按照相同训练规则更新，主要差别是 Harness 怎样利用反馈。（现阶段这些，后面还要增加现有方法作为 baseline 甚至是自己创造）

| 对照方法 | 具体运行方式 | 与本方法比较什么 |
|---|---|---|
| 固定 Harness + ReAct | 根据当前结果调用数据工具，可以调整当前批次方案，但运行规则和 Skill 不持续改写 | Harness 更新是否带来超出即时决策的收益 |
| ReAct + Reflexion | 在上述方法上保存反思文字，供后续批次读取，程序与流程仍固定 | 可执行修改是否优于只积累反思经验 |
| 通用 Self-Harness 适配 | 使用同样的可修改组件和运行记录，直接让 LLM 提出局部修改并验证，不使用依赖关系引导的成组搜索 | 组织修改对象的方法是否有效 |
| CurateEvo 适配 | 根据失败反馈修改数据整理代码，其他 Harness 机制固定，接入相同任务训练接口 | 改进完整数据 Harness 是否优于只改数据处理代码 |

[CurateEvo](https://arxiv.org/abs/2607.06140) 原始设置使用固定原始语料。接入长程数据流属于适配版本，需要明确说明差别，不把适配结果写成原论文结果。其他论文方法接入新任务时同样说明保留和调整了什么。

再保留两个直接对照：将本方法改成逐组件独立修改，检验成组修改的作用。将候选检查从连续 3 批改成当前 1 批，检验后续收益检查的作用。各方法的候选训练、失败尝试和人工请求均计入总预算，不能只统一轮数而忽略计算差异。

主要结果是相同总成本下，各批次和最终任务模型的真实人工偏好表现，同时报告平局、不满足要求的比例与人工耗时。模拟反馈结果单独展示，不能替代真人结果。

长程比较保留完整表现曲线，以及最终表现相对历史最好开发表现的变化。若发生退步，记录达到预先确定恢复标准所需的批次数。最终隐藏测试只用于报告，不返回给候选选择程序。

此外，将运行前后的 Harness 放到相同的新任务、相同模型起点和初始数据上比较，检查更新后的方法是否更会改进数据。再提供相同初始经验材料，区分流程更新和单纯积累更多经验的作用。不同 Memory 结构按各自方式读取同一份材料，不要求使用相同内部格式。



总的来说，我们希望验证的研究假设是，数据 Harness 的改进需要同时考虑组件依赖、可执行的经验更新和后续训练效果。技术重点是将文字反思转成成组修改，再通过连续运行选择修改，使系统在不更新决策 LLM 参数的情况下持续改善数据处理方法。这些思想分别与 ReAct、Reflexion 和既有 Self-harness 研究相关，而我们的新意需要体现在针对数据系统的联合更新方法及其实际收益上。
