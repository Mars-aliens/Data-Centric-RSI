# Data System 长周期自进化框架

## 目标

当前研究路线是保障 Data System 长周期稳定运行。此前技术一组件演化协议和结果仅作历史归档；本架构不迁移、不覆盖旧 runner 或结果。新流程使用 `DataSystemEvolutionRuntime`，不把旧的单次 held-in 接受规则解释成新的长期版本选择方法。

## 研究与运行顺序

研究构建顺序为 T1 → T2 → T3 → 组合与消融 → 长周期压力测试。完整系统在线运行时为：

```text
连续任务
→ T3 将反馈归因到来源版本
→ T2 检查并治理可复用经验
→ T1 在隔离环境检查候选修改
→ T3 收集成对的后续批次表现
→ T3 决定接受、继续观察或保持稳定版本
→ 下一轮任务
```

## 代码边界

- `code/core_system/mle_core/evolution.py`：系统版本向量、候选版本和带来源批次的反馈事件。
- `code/technologies/technology_one/candidate_gate.py`：安全检查。通过只表示候选可以进入观察，不会改变稳定版本。
- `code/technologies/technology_two/experience_lifecycle.py`：经验来源、适用条件、验证、失败、冲突、失效和检索状态。
- `code/technologies/technology_three/version_selection.py`：反馈版本归因和候选多批次观察/决策接口。
- `code/integration/runtime.py`：跨技术编排和稳定版本状态更新。

经验状态、未完成的候选观察窗口和已晋升的稳定版本从 append-only 事件日志重放，进程重启后可继续观察或恢复到先前晋升版本。该机制目前是本地框架的可恢复性骨架，尚未覆盖并发写入、分布式执行或大规模日志压缩。

## 候选生命周期

```text
候选提出
→ T1 安全检查
  ├─ 未通过：记录失败，稳定版本不变
  └─ 通过：进入后续批次观察，稳定版本仍不变
       → T3 汇总与稳定版本配对的运行结果
         ├─ 证据不足：继续观察
         ├─ 未达到保留规则：保持稳定版本
         └─ 达到保留规则：提升候选为稳定版本
```

这里的 `PairedMeanRetentionPolicy` 只是可运行的占位基线，不是已确定的论文算法。正式实验前需要冻结指标方向、观察窗口、退化容忍度、成本约束和统计规则，并与其他选择策略比较。

## 经验生命周期

新经验只能从 `candidate` 状态开始。只有显式验证后才可检索复用；重复失败或适用条件发生变化后进入 `needs_validation`；冲突经验在解决前不参与检索。每条经验保留来源系统版本、运行和批次。

## 兼容与边界

- 旧技术一 runner、配置和历史结果不迁移、不覆盖。
- 新候选流程不以安全检查结果代替长期效果评价。
- `held_out` 只能用于报告；`final_test` 只允许在系统冻结后独立评估。
- 本骨架提供可执行接口和本地测试，不代表 T1/T2/T3 的研究算法或长周期收益已经验证。
