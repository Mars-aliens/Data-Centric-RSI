# Data System 长周期实验任务定义

版本：Task Definition v1
状态：任务语义、数据分区、批次和反馈时序已冻结；正式实验的模型 revision、预算、随机种子数和统计方案仍需单独冻结。

## 1. 研究任务

本项目研究一个持续接收数据、构建训练集并更新下游模型的 Data System，能否在连续运行中安全地改进自己的数据处理与运行方法。系统每轮接收一批新任务数据及已到期反馈，决定如何筛选、清洗或转换数据，按固定训练规则更新 Task Model，并可提出对 Harness、Memory 或 Skill 的候选修改。运行结果、数据、模型和系统方法都必须版本化；候选修改失败时，当前稳定系统仍应能继续运行或恢复。

研究对象不是单次回答质量，也不是让 Decision LLM 本身持续训练。Task Model 的任务指标用于衡量 Data System 产出的训练数据是否有用；三个技术点共同研究系统能否长期、可审计、可恢复地持续执行。

## 2. 主任务与数据含义

首个共同基准采用固定 revision 的 `nvidia/HelpSteer2`，构造**按提示词分组的回答质量三分类任务**：输入一个 prompt-response，预测该回答在同一 prompt 的候选回答中的相对质量标签 `preferred`、`rejected` 或 `tie`。

HelpSteer2 的五个评分维度为 `helpfulness`、`correctness`、`coherence`、`complexity`、`verbosity`。当前适配器将五项评分的算术平均作为组内排序值：最高为 `preferred`，最低为 `rejected`，严格位于两端之间的记录为 `tie`；若组内所有平均分相同，则全组为 `tie`。评分原值与派生标签必须同时保留，供审计和替换标签规则时使用。

任务定义 v1 对提示做换行符统一和首尾空白清理，之后以完全相同的 prompt 作为一个 group。少于两个回答的 singleton group 不参与分组分类，必须在 manifest 中计数，不得静默丢弃。每项评分必须是有限的 `[0, 4]` 数值。该等权平均标签是本实验的操作性目标，不应解释为 HelpSteer2 官方综合偏好标签。

此任务测量的是基于 HelpSteer2 群组评分构造的分类代理任务，不等同于个体用户偏好建模，也不代表真实用户的长期偏好变化。该数据集没有用户/session 身份，也没有天然时间顺序。把它排列成连续批次、隐藏并延迟释放已有标签，属于可复现的**受控流式回放**，不能描述为真实在线用户反馈或自然发生的长期漂移。

## 3. 任务输入与信息边界

每次运行开始时固定并记录：

- 数据集 revision、规范化/标签构造规则、分组与划分清单、流顺序及其随机种子；
- 初始 Data System 版本向量，包括 Harness、Memory、Skill、数据版本、Task Model 检查点、训练配方和 evaluator；
- Decision LLM 与 Task Model 的模型 ID/revision、工具版本及总预算；
- 反馈释放计划、运行批次数、故障注入计划和停止条件。

每批输入由当前稳定版本、该批新到的完整 prompt group、此前已释放的反馈、运行历史、剩余预算和本批运行约束组成。prompt group 是不可拆分单位；同一 group 的候选回答、派生记录和增强样本必须始终留在同一数据划分中。

系统只能读取当前批次及此前已释放的信息。未来批次的记录、尚未到释放批次的评分/标签、`held_out` 标签和 `final_test` 数据均不可进入 Decision LLM、Memory/Skill 检索、训练集构建或候选选择。未到期反馈可以记录为 pending，但其值必须不可见。

反馈延迟 `0/2/5` 表示完成来源批次之后，经过 0、2、5 个完整批次边界再释放标签。对来源批次 `b`，标签在 `b + delay + 1` 批次开始时可用；因此 delay 0 也不会在当前批次处理过程中泄漏标签，只会在当前批次结束后、下一批开始时释放。完整流结束时，可信分析端可补算终态边界前已到期的指标，但结果不再回灌 agent 或影响版本选择；更晚的反馈保持 pending。它是对已存在评分的延迟回放，不是真实人工反馈延迟。若实验需要人工反馈成本或真实偏好，必须另设人工标注实验，不能从该模拟回放推断。

## 4. 每批处理与输出

系统每批完成以下逻辑闭环：

1. 在批次开始时释放已到期标签与此前批次的预序列评测结果。
2. 接收当前完整 prompt groups 的无标签输入；Task Model 先对当前批次预测，预测必须绑定生成它的 Data System/模型版本。
3. 按当前 Harness 处理已到期的有标签池。每批从各分支自己的上一 checkpoint 继续训练；候选分支和稳定分支从相同父状态分叉，接收相同的新输入、反馈和批次顺序，不能共享新产生的模型、Memory、Skill 或数据工件。具体训练数据选择由各自 Harness 决定，但每批预算上限相同，所有实际消耗均计入。
4. 候选安全检查、经验检索和版本观察按 T1/T2/T3 执行。当前批次标签不会用于本批的预测、筛选或更新；其反馈在批次完成后进入延迟队列。
5. 在标签到期时，可信评测器才对当时已提交且绑定来源版本的预测计算预序列指标；该指标可作为后续 T3 证据。完整流结束时，可信分析端可补算终态边界前已到期的指标，但结果不再回灌 agent 或影响版本选择；更晚的反馈保持 pending。状态、待处理反馈和事件日志持久化，以支持审计和恢复。

每批输出至少包括：新数据集工件与来源图、Task Model 检查点与训练配方、各 split 指标、收到/待处理反馈清单、Data System 全版本向量、提案与检查/选择结果、失败与恢复事件、预算消耗和完整性审计结果。仅新增数据或检查点，不自动算作 Harness/Data System 改进；必须证明其可被后续运行正确使用并满足预先冻结的评价条件。

## 5. 数据划分与运行流

划分和流顺序均以完整 prompt group 为单位，使用可复现的清单及哈希记录：

| 分区 | 用途 | 可见性与限制 |
| --- | --- | --- |
| `seed` | 启动系统时提供的初始有标签训练案例 | 运行开始时可用；不得与其他分区共享 group |
| `development` | 按批次进入的运行流数据 | 当前批先以无标签输入进入；标签按反馈时序释放。模型先预测，标签释放后以预序列指标评估 |
| `held_in` | 方法与参数的离线开发 | 仅在正式协议冻结前用于开发；正式运行期间不用于逐批候选选择，避免反复适配同一静态集合 |
| `held_out` | 冻结前的回归报告集 | 仅由可信评测器报告；不得进入策略、训练、Memory/Skill 或 T1/T3 决策 |
| `final_test` | 系统与分析方案冻结后的最终报告 | 官方 validation 映射到此 split；冻结前完全锁定，不向运行系统提供数据或标签 |

任务定义 v1 固定把官方 train prompt groups 按 `SHA256(group_id)[:8] mod 100` 分配为 `seed=10%`、`development=60%`、`held_in=15%`、`held_out=15%`；官方 validation 的完整 prompt groups 全部映射为 `final_test`。分组和流顺序清单分别写入 manifest 并计算哈希。development 按 `SHA256(f"{stream_seed}:{group_id}")` 排序，每批 50 个完整 prompt groups，最后一批允许不足 50 组。反馈延迟是 run 级参数，只允许 `0/2/5`。

runner 可选接受正整数 `max_batches`，只排程确定性 development 流的前 N 批，用于真实模型 smoke 和故障调试；它不改变数据分区或 group 排序。manifest 同时记录完整可用 development 批次数、实际排程批次数、`max_batches` 和是否截断。正式全流实验不设置该参数。短流结果不得与完整流结果合并统计。

每个 run 的流必须由唯一 prompt groups 组成；不得重复样本来凑批次或延长周期。所有实验臂使用同一划分、同一流顺序和同一反馈释放表。由于 HelpSteer2 没有时间戳，顺序由固定 `stream_seed` 的确定性哈希排列产生，只能称作“随机化受控回放顺序”。同一 run 内稳定版本和候选版本获得完全相同的任务输入和反馈到达时序。

运行长度由可用且未重复的 `development` prompt groups、每批 50 组和预算共同决定。按此前观测到的约 10,161 个 train prompt groups，v1 预计最多约 122 个 development batches；正式准备时必须以当前下载文件重新计算 manifest。100 批运行要求至少 5,000 个 development groups；HelpSteer2 单独不支持 300 批×50 组。不得重复记录凑周期；若需更长运行，应另行注册不同任务流的外部验证，不得混合结果仍称同一任务。

## 6. 三个技术点在共同任务中的可检验作用

| 技术点 | 在任务中的处理对象 | 必须观察的稳定性结果 |
| --- | --- | --- |
| T1 安全自进化与故障隔离 | 对 Harness、数据处理规则、Memory/Skill 或相关运行配置提出候选；候选在独立状态中检查和执行 | 候选错误是否被隔离；稳定版本、数据、检查点和日志是否未受污染；后续批次能否继续；恢复是否成功及耗时 |
| T2 可执行经验生命周期管理 | 将批次诊断转成带来源、版本、条件与验证状态的经验/Skill，并决定后续是否可检索 | 错误或冲突经验是否阻断复用；条件变化后是否重新验证/失效；经验增长、检索成本和任务连续性是否可控 |
| T3 基于后续运行表现的更新保留与回退 | 将反馈归因到产生它的数据、模型和 Data System 版本；在后续批次观察候选与稳定版本 | 延迟反馈是否归因正确；是否避免过早晋升；真实退化时是否保持/回退；最终运行质量与恢复能力如何 |

三个技术点的独立实验先分别检验机制，再在相同任务流和预算下进行组合与消融。在线闭环可表述为：

```text
接收连续批次与到期反馈
  -> T3 依据来源版本整理可用证据
  -> T2 检查适用经验并提供可复用方法
  -> T1 隔离执行新的系统候选
  -> 后续批次继续运行并累计成对证据
  -> T3 决定继续观察、保留、拒绝或恢复
  -> 下一批
```

研究构建顺序仍为 T1、T2、T3、组合与消融；上图描述系统全部具备后的在线运行顺序，两者不矛盾。

## 7. 评价与完整性通过条件

实验必须同时报告以下四类结果，不能用单一准确率或“进程未崩溃”代表长周期稳定：

- **任务质量**：held-in/held-out 的 macro-F1、accuracy 和各类指标随批次变化；`final_test` 仅在冻结后报告。
- **数据完整性**：分组泄漏数、重复率、标签可见性违规、来源字段完整率、无效数据率及派生数据可追溯率。
- **运行稳定性**：目标批次完成率、受控失败率、候选故障隔离率、恢复成功率/时间、回滚正确性、检查点连续性及未恢复中断数。
- **资源与治理**：LLM 调用/token、训练步数/时间、评价调用、反馈请求、Memory/Skill 规模与检索成本、预算超限次数。

一项 run 只有同时满足下列条件才算“任务完整完成”：

1. 所有计划批次均完成，或在明确标注的预算/故障停止条件下以可解释状态结束；不能静默丢批。
2. 全部输入、派生数据、模型、评价、反馈与系统版本具备来源关系和校验哈希。
3. 没有 prompt group 跨 split，没有未释放标签泄漏，没有 `held_out`/`final_test` 参与选择。
4. 注入故障有可重现记录；失败候选不能污染 active 版本，恢复后的运行状态与检查点可审计。
5. 所有对照遵守相同任务流、初始状态、模型与资源预算；实际消耗和失败尝试也计入报告。
6. 任务质量和稳定性结果分别报告；不以高接受率、低拒绝率或单次成功作为方法有效的证据。

## 8. 当前实现状态与安全边界

新模块 `technology_one/long_horizon_task.py` 已实现任务数据契约、分组标签、train group 切分、受控流顺序、无标签批次视图、反馈释放、版本绑定预序列评测、终态离线汇总和调度/Oracle 状态恢复。预检 bundle 的 `agent-visible/` 只含 seed 与 manifest；未来 development 输入及释放时间表位于 `runner-only/`，必须通过文件权限或独立挂载隔离，不能只依赖目录命名。`scripts/prepare_long_horizon_task.py` 可从本地原始 split JSONL 生成统计 manifest 和预检 bundle；真实数据未包含在仓库中。它不改写旧适配器。当前实现仍是可信 runner 内的 Python 边界，不是对抗性安全沙箱：不得把 `FeedbackOracle` 或 gold store 的对象引用交给 Decision LLM、候选代码或 Task Model；未来若允许不可信候选代码，必须把 oracle 放入独立进程/权限域，仅经受限 API 提供已释放反馈。

正式实验前还必须：用实际固定 revision 的数据文件生成 manifest，检查实际 group counts、类别占比、批次数和最后批大小；在真实模型和服务器上 smoke 固定流式 Qwen runner，确认预序列预测及 parent checkpoint 续训只使用 seed 加已释放反馈；将新 T1/T2/T3 runtime 接入真实分批执行、候选隔离与故障注入。HelpSteer2 标签是组内质量代理目标，不能支持个体偏好或自然漂移结论。

因此，下一步是生成真实数据 manifest 并审计实际数据，再完成真实 Task Model 的 parent-checkpoint 固定流水线 smoke。通过这些门槛后，才启动新 T1/T2/T3 端到端实验。此前技术一代码和运行结果不包含在当前 GitHub 项目中，也不作为新三技术的前置工作或验证证据。

## 9. 正式运行前还需冻结的实验参数

任务语义已经定义，但下面这些实验参数不能从任务描述中臆造，需形成单独、版本化的正式协议：

- Decision LLM、Task Model、evaluator 的精确 revision 与训练配方；
- 多随机种子列表、每个任务臂的总批数以及 `0/2/5` 延迟条件的实验分配；
- 每臂各类资源预算、失败注入类型/频率、停止与恢复阈值；
- 主要统计终点、非劣界值/稳定性阈值、随机种子数和统计检验；
- 是否将 CoAuthor 或 PRISM 作为独立外部任务验证。它们不能与 HelpSteer2 的 group-relative 分类结果直接合并。

其中任务切分、流顺序、批量大小、反馈边界及 smoke 专用流前缀限制已由 Task Definition v1 实现；实测 group counts 与 manifest 哈希仍须在服务器预检时确认。其余参数冻结前，可运行 schema、泄漏、反馈队列和故障恢复测试；不得将其结果称为正式长周期有效性结论。
