# MLE-LEGO 实验总蓝图 v1

状态：详细设计与审计字段稿。当前执行顺序和实验阶段以[当前实验方案 v2](current-experiment-plan-v2.md)为准；本文保留各 QA 的细化设计，不把计划中的服务器结果写成已完成结果。

## 1. 统一任务与比较单位

- **数据集**：HelpSteer2 固定 revision `990b2711a36180dd19d9c94b8627844866f8982a`。任务将同一 prompt 的 responses 聚合成 `preferred/rejected/tie` 三分类，按完整 prompt group 划分，不能拆散同一 group。
- **运行流**：固定任务定义中的 seed/development/held-in/held-out 划分和确定性 development 顺序；每批 50 个 prompt groups；反馈延迟 pilot 默认 2 批。HelpSteer2 没有自然时间戳，因此这是受控回放，不等于真实用户在线时间漂移。
- **模型**：候选修改隔离实验与数据经验治理实验共用本地 Qwen3-8B Task Model、同一不可变权重 revision、Tokenizer、LoRA 配方和训练预算。具体路径由服务器私有配置提供。候选修改隔离实验的真实提案阶段使用固定 Decision LLM；数据经验治理实验不调用 Decision LLM；延迟反馈归因与版本选择实验的离线回放不加载模型。
- **配对单位**：`seed × stream_seed × 数据 manifest × Task Model revision × 训练配置 × 反馈延迟`。同一配对单位下所有实验臂使用完全相同的 prompt groups、顺序和反馈释放时间。跨 seed 分别成对分析，不能把不同数据流当作同一条流。
- **信息边界**：当前 development 批只能先预测后释放标签；经验构建和版本决策只看已释放信息。held-out 只可信报告，final-test 在方案冻结前锁定。所有 summary 必须标记 `held_out_used=false`、`final_test_used=false`。
- **运行单位**：smoke 只验证工程链路，不计为方法有效性结果；pilot 先用 seed `17/23/29`、每个 run 10 批。候选修改隔离实验的工程 smoke 使用 4 批。正式全流长度、种子数、统计检验和阈值须在 pilot 后另发 protocol v2 冻结。

## 2. 候选修改隔离与运行连续性实验

### QA1：候选出错时，错误会不会污染稳定数据处理流程？

| 项目 | 设计 |
| --- | --- |
| Baseline | `B0-fixed`：固定 Data System，不运行候选。配对控制为同一候选修改隔离实验 run 中继续运行的 stable branch。 |
| 实验臂 | `T1-shadow-clean`：固定可信 runner 在独立 candidate 分支运行受限数据策略；`T1-shadow-fault`：在 candidate 第 4 批注入一种预先登记故障。每类故障单独 run。这些名称是现有运行配置标识。 |
| 数据 | HelpSteer2 同一 4 批 smoke 流；Pilot 延伸为 10–20 批。候选和 stable 接收相同公开输入、相同已释放反馈。 |
| 评估 | 故障检测率、故障隔离率、stable 完成批次/计划批次、stable checkpoint 故障前后哈希、候选 parent 是否只读、重复/丢失反馈数、失败原因是否可审计、恢复成功率/耗时。 |
| 结果呈现 | **表 隔离-A**：每类故障、注入批次、检测 code、candidate 状态、stable 是否完成、checkpoint 哈希是否不变、恢复结果。**图 隔离-A**：批次时间线，标出故障注入/检测点及 stable/candidate 状态。**图 隔离-B**：stable 完成率与故障隔离率，按故障类型分组；报告分子/分母，不只给百分比。 |
| 通过标准 | Smoke 至少完成 clean 4/4；`invalid_protocol` 注入后 candidate 被拒绝、stable 仍 4/4、stable checkpoint 哈希不变、无反馈重复。Pilot 的所有预登记故障逐类报告。 |

## 3. 数据经验持续治理实验

### QA1：把经验变成数据处理动作，是否比只写反思或不保留经验更有帮助？

### QA2：经验带来源、适用条件并在条件变化后暂停重验，是否比无治理复用更稳定？

| 项目 | 设计 |
| --- | --- |
| Baseline/实验臂 | `no_experience`：不存持久经验；`reflection_only`：存标签分布反思但不改变训练数据；`executable_unmanaged`：经验规则首次观察后立即执行，遇到条件变化仍沿用；`lifecycle_governed`：新经验至少跨两个反馈批次观察，条件匹配并通过覆盖检查才执行，条件变化后暂停并重新验证。 |
| 可执行经验 | 固定确定性数据选择 Skill：累计已释放训练记录按类别计数，各类保留上限为当前最少类别的 2 倍，保留较新的记录。不是 LLM 生成的策略；结论只适用于该规则。 |
| 数据 | HelpSteer2 同一数据 revision 和同一 prompt-group 流；每 seed 四臂配对。Smoke `seed=17,max_batches=4`；Pilot seeds `17/23/29,max_batches=10`，同 GPU 串行。 |
| QA1 主要评估 | `executable_unmanaged` 对 `reflection_only`，以及 `reflection_only` 对 `no_experience`。观察经验实际执行后的每批 Macro-F1/Accuracy、数据保留率、训练记录数和训练成本。 |
| QA2 主要评估 | `lifecycle_governed` 对 `executable_unmanaged`。观察经验启用/暂停批次、条件变化后误复用数、重新验证批数、类别覆盖、每批质量退化幅度、恢复到旧质量的批数。 |
| 全部评估 | 完成率、逐批与总体预序列 Macro-F1/Accuracy、类别混淆矩阵、数据选择前后各类计数、经验来源/条件/状态完整率、经验库大小、训练和推理成本、checkpoint 恢复情况。 |
| 结果呈现 | **图 经验-A**：四臂逐批 Macro-F1 折线，标经验创建、启用、漂移、暂停和重新验证批次；**图 经验-B**：每 seed 的三组配对差值（治理-无治理、可执行-反思、反思-无经验）；**图 经验-C**：每批各类别训练记录数，展示筛选影响；**表 经验-A**：seed 级质量/成本/完成率；**表 经验-B**：经验生命周期审计（条件、来源、状态转换、误复用、重验批数）。 |
| 解释限制 | 4 批 smoke 主要检查运行与治理状态；经验实际执行的效果应以 10 批 pilot 观察。标签分布来自已释放反馈，是受控条件，不等价于外部自然漂移；治理臂的覆盖检查不是下游效果证明。 |

## 4. 延迟反馈归因与多批次版本选择实验

### QA1：反馈按到达时间而非来源版本处理，会造成多少版本错配？

### QA2：多批次来源配对是否比看一个批次更不容易做出不稳定的保留决定？

| 项目 | 设计 |
| --- | --- |
| 输入数据 | 每个 seed 已完成的候选修改隔离实验 stable/candidate run summary；提取每个来源批次的版本 ID、stable/candidate Macro-F1、反馈 `available_from_batch` 和候选失败状态。本实验不重新训练模型。 |

  feedback-trace.json        # T3

每个最终图表同时展示 seed 级数据、样本/批次数、误差或区间定义；每张表都包含各臂的实际完成数和预算消耗。不能只展示平均分、只展示被接受候选，或删除失败 run。

## 9. 深化后的可验证设计

本节把前面的 QA 转成可执行、可否定的实验。下面的实验条件属于设计方案；标记为“需实现”的内容不能当作当前 runner 已支持。

### 9.1 统一分析规则

| 项目 | 预先固定的规则 |
| --- | --- |
| 独立比较单位 | 一个 `seed × stream_seed × 数据流 manifest × Task Model revision × 训练配置`。同一单位下的实验臂成对比较；每个 seed 是一个独立重复。 |
| 观测单位 | 批次用于画运行轨迹和定位转折点，不作为独立统计样本。不能把 10 批 × 3 seeds 报成 30 个独立样本。 |
| 试运行规模 | 工程 smoke 验证接口与不变量；pilot 使用 3 个配对 seed。pilot 只给效应量、seed 级差值和区间，不声称正式显著性。正式 seed 数根据 pilot 的配对差值方差和预注册的最小有意义差异计算。 |
| 数据与模型锁定 | 所有臂使用同一数据 revision、分组清单、流顺序、反馈延迟、初始 checkpoint、训练预算和评价程序。每个 run 保存 manifest/config/model hash。 |
| 失败处理 | 运行失败、候选无效、预算超限和提前停止都保留在原实验臂分母中，另报原因；不得只分析成功或被接纳的候选。 |
| 结论门槛 | 机制不变量用逐例通过/失败判断；效果比较报告 seed 配对差值及不确定区间。pilot 后、查看 held-out 前冻结正式的最小有意义差异、非劣界值、停止规则和统计方法。 |
| 指标分层 | 稳定运行、数据处理行为、下游任务质量、资源成本分开报告。质量提高不能替代完整性证据，流程完整也不能单独证明数据策略有效。 |

### 9.2 候选修改隔离与运行连续性

#### QA-I：候选失败是否只影响候选分支？

**可证伪假设**：预登记的候选故障会被检测并留在候选分支；稳定分支的已提交数据、反馈队列、预测文件和 checkpoint lineage 与无候选对照一致。

| 要素 | 具体设计 |
| --- | --- |
| 对照组 | 固定流水线 `B0-fixed`；相同流的候选 clean run；相同流、逐类单独注入故障的 candidate run。 |
| 故障条件 | 首轮覆盖 `invalid_protocol`；完整故障矩阵逐类覆盖 `timeout`、非零退出、非法 JSON、错误 parent、缺失预测、非法标签、预算超限和父 checkpoint 写入尝试。每个 run 只注入一种故障，故障批次固定并写入 manifest。 |
| 主终点 | 故障隔离成功数 / 注入故障数。一次成功必须同时满足：有明确 failure code；candidate 在该批终止或拒绝；stable 完成计划批次；stable checkpoint 与预测/反馈账本未被候选写入；无重复或丢失已提交反馈。 |
| 次终点 | clean run 的误拒绝率、稳定分支完成率、candidate 失败检测延迟、candidate 额外 GPU/CPU/时间成本、每类故障的恢复情况。 |
| 判读 | 任一故障导致 stable 版本或账本改变，即该故障类型隔离失败；clean run 被拒绝计为误拒绝。pilot 报告逐故障分子/分母；只有每类故障在预注册重复中均满足不变量，才支持该实现范围内的隔离主张。 |
| 结果呈现 | **故障逐例表**：`seed, fault_type, injection_batch, detected, failure_code, candidate_terminal_batch, stable_completed, stable_hash_before, stable_hash_after, duplicate_feedback, missing_feedback, recovery_result`。**时间线图**：批次为横轴，stable/candidate 状态为泳道，标出注入、检测和终止位置。 |
| 结论边界 | `local_shadow` 验证可信 runner 的分支与协议边界，不证明任意候选代码具有 OS/容器级隔离。若要声称强隔离，需单独以恶意写文件、越权路径、网络和资源耗尽为威胁模型验证。 |

#### QA-II：候选数据策略对质量、数据使用和成本的净影响是什么？

**可证伪假设**：候选相对固定流程产生可重复的 held-in 预序列质量或数据处理收益，且收益不是通过额外预算或选择性报告得到。

| 要素 | 具体设计 |
| --- | --- |
| 对照组 | 同一个初始 Task Model 和流上的固定 stable 分支；候选分支从同一 parent 分叉，获得相同公开输入及已释放反馈。候选通过安全门与候选最终被保留是两个不同事件，分别统计。 |
| 候选集合 | 每个 seed 使用预先登记的候选修改模板；记录所有 LLM 提案，包括格式无效、无变化、重复和评估退化者。一个候选不能代表提案方法整体。由于 candidate bundle 绑定 parent 版本，跨 seed 冻结和复用的是语义修改模板，不是带旧 parent binding 的 bundle；每个 seed 都要重新生成并校验 bundle。Decision LLM 生成质量另按提案级记录。 |
| 主终点 | 来源批次对齐的 `candidate_macro_f1 - stable_macro_f1`，先逐批计算，再按 seed 汇总平均差、最差批差和正收益批次比例。最终观察标签只在反馈释放后计分，绝不回流到当前预测或选择。 |
| 数据行为 | 每批候选与 stable 的训练记录 ID 集合、各类保留数、丢弃数、覆盖率和数据来源；对共同保留/差异保留样本做集合差分析。当前只记录数量的地方，需补逐记录 ID 或可复算选择摘要。 |
| 成本终点 | 同时报训练步数、训练/预测秒数、GPU 峰值显存与利用率、额外 LLM 调用/token、候选失败消耗；同时报每增加 1 个百分点 Macro-F1 的增量成本，若无正收益则不计算该比值。 |
| 判读 | 若配对质量差未达到正式预注册的最小有意义差异，结论是“未证明候选有实用质量收益”；若质量改善但稳定性不满足非劣界值，不能称为整体改进。smoke fixture 只验证链路，不进入该效应估计。 |
| 结果呈现 | **质量轨迹图**：来源批次 Macro-F1，画 stable/candidate 与 seed 级配对差；**数据选择图**：每批各类别输入/保留/丢弃量；**候选结果表**：每个提案的 hash、验证结果、重复状态、质量差、成本、失败原因和最终状态。 |
| 当前边界 | 当前 runner 侧跑 candidate 与 stable，但不会把 candidate 自动提升为后续 active 版本。因此这个 QA 评估候选效果，不证明递归晋升后的长期系统收益。 |

#### QA-III：中断恢复能否做到逻辑状态等价且不重放？

**可证伪假设**：在批次边界中断后，从 checkpoint 恢复的逻辑结果与不中断运行一致，且已提交批次和 feedback ID 不重复、不丢失。

| 要素 | 具体设计 |
| --- | --- |
| 对照组 | 同一 seed/config 的 uninterrupted run；中断组在批次 1、3 和 pilot 中点完成提交后停止，再用相同 run ID、路径和配置恢复。每次中断位置作为单独配对 run。另行注入一次命令失败，不能和进程中断混为一类。 |
| 比较字段 | `completed_batches`、batch ID 顺序、feedback ID 集合、每批预测 checksum、active checkpoint version/parent 链、Task Model 累计训练记录数、candidate trial 数、最终 held-in 预序列 confusion matrix。 |
| 主终点 | 所有逻辑状态字段与不中断组完全一致；重复批次数、重复反馈数、漏批数、漏反馈数均为 0。时间和重试次数作为成本次终点，不要求与 uninterrupted 完全一致。 |
| 判读 | 任一逻辑字段不同都记为恢复不等价，不能用最终 Macro-F1 相近掩盖状态差异。恢复成功率按中断类型和位置分别报告。 |
| 结果呈现 | **恢复等价表**：中断位置、失败类型、恢复耗时、批次/反馈集合差异、checkpoint lineage 是否一致、最终逻辑状态是否相同。**状态时间线图**：标记首次执行、提交、停止与恢复区间。 |

### 9.3 数据经验持续治理

#### 先准备可控的数据条件变化

HelpSteer2 原始数据没有时间戳，哈希随机顺序不能保证产生清晰的分布漂移。因此只在原始随机流上观察到的条件变化，不能支撑“漂移下治理有效”的结论。需从同一 development prompt-group 集构造并冻结三种无重复流清单：

| 流条件 | 构造和用途 |
| --- | --- |
| 平稳流 | 固定 seed 分层打散，尽可能让相邻批次的类别比例稳定；作为无漂移对照。 |
| 单次突变流 | 在预注册批次边界前后调整 group 顺序，使到达批次的类别分布产生可测变化；用于触发生命周期暂停与重验。 |
| 反复变化流 | 在两种预先定义的类别分布状态之间切换；用于检验经验反复失效时是否会持续误用、频繁重验或无法恢复。 |

流构造器可以在离线准备时读取标签来安排 group，但运行中的 policy 只能看到按既定延迟释放的标签。每种流需保存算法版本、每批真实类别比例、group ID 清单和 manifest hash；所有四个经验臂共享同一条流。必须先检查实际类别数是否足以构造目标比例；目标比例和突变点在查看实验结果前冻结。该实验是对可控标签分布变化的鲁棒性测试，不等价于自然用户漂移。

#### QA-IV：可执行经验本身是否改变数据与下游结果？

**对照**：`no_experience`、`reflection_only`、`executable_unmanaged`。三臂使用完全相同的平稳/突变/反复变化流。

**主要计算**：对每个 seed 与流条件，计算 `executable_unmanaged - reflection_only` 的配对预序列 Macro-F1 差，以及 `reflection_only - no_experience` 的差；同时计算每批训练数据保留率 `records_selected / records_before`、各类样本数和训练成本。治理规则观测的是“本批新释放反馈”的类别比例；反馈延迟为 2 时，真实输入流的变化到策略看到变化之间至少存在释放延迟。因此同时报告流变化批次、反馈可见批次和策略响应批次，不能把响应时间全归因于治理算法。

**可支持的结论**：只有规则实际改变了被训练的数据，且相应下游质量/成本变化在 seed 间可复现，才能说明“可执行数据经验改变了 Data System 行为”。若数据选择改变但质量无改善，结论应写成“改变了数据暴露，没有证明下游收益”。

#### QA-V：条件治理能否减少失效经验误用并控制恢复代价？

**对照**：`lifecycle_governed` 对 `executable_unmanaged`；重点比较单次突变和反复变化流。平稳流用来量化治理造成的等待成本和误暂停。

| 量 | 操作定义 |
| --- | --- |
| 误用 | 已知经验条件与当前批观测条件不一致时仍 `experience_applied=true` 的批次数。 |
| 暂停延迟 | 分别报告真实流变化批次到变化反馈释放批次、反馈释放批次到经验停止应用批次，以及变化起点到停止应用的总批数。理想策略反应是不晚于变化被检测的同一批停止应用。 |
| 重验时长 | 条件变化被检测到重新进入 verified 并再次应用之间的批数；同时报告未能重验的经验数。 |
| 任务代价 | 突变后若干批的 Macro-F1 配对差、类别覆盖变化、额外训练记录/时间；窗口长度在正式实验前冻结。 |
| 平稳流代价 | 治理臂相对无治理臂的激活延迟、累计丢弃数据量和 Macro-F1 差，避免只报告漂移获益。 |

逐批 audit 已记录 `conditions_before`、`conditions_observed`、`context_changed`、经验状态前后值、来源批次/版本及所选记录 ID/hash；这些字段仍需在本地定向测试和服务器 smoke 中验收后，才能用于计算 QA-V。若字段缺失或不能由逐批历史复算，误用率结果不成立。

**判读与展示**：治理的目标不是所有情况下 Macro-F1 都高于无治理，而是在条件变化时显著减少不匹配经验生效，并把质量损失/重验成本控制在预注册范围内。呈现三条流条件的逐批质量图（标出真实突变点和经验状态），以及每 seed 的误用、暂停延迟、重验时长、质量损失和成本配对表。

### 9.4 延迟反馈归因与多批次版本选择

#### QA-VI：来源归因在延迟和乱序到达时是否仍正确？

做两层实验，不能混为一个结论。**归因单元测试/离线敏感性回放**：从同一组 stable/candidate 来源分数构造到达延迟 `0/2/5` 批的轨迹，分数和 source ID 不变，只改变可用时间，用来单独检查归因和选择规则对到达时序是否敏感。**端到端延迟对照**：分别以 `feedback_delay=0/2/5` 重跑候选修改隔离实验，因为延迟会改变每批可训练数据及后续 checkpoint，不能只改已有轨迹的时间戳来推断模型或数据系统的延迟效应。再构造一个仅供诊断的错误基线，把 arrival order 当作 current version。延迟队列在数据不足时须标明“仍 pending”，不能为了凑齐窗口而使用未来反馈。

**主指标**：来源版本匹配准确率（正确匹配事件数/全部到达事件）、字段完整率、错归因数，以及从来源产生到证据可用的批数。压力条件包括同一批多个版本反馈、跨版本交错到达和窗口边界晚到。

**必需数据**：`feedback_id, source_batch_index, source_version_id, available_from_batch, target_version_at_arrival, matched_version_id, matching_rule, decision_batch_index`。现有轨迹保留 source 与 arrival 信息，但要检验错误匹配处理，需加入乱序/字段缺失/未知版本的构造 fixture 和逐事件审计。

**判读**：source-aware 处理必须把每条反馈关联回唯一来源版本；缺失来源信息应进入 unknown/pending 并阻止其影响版本选择，不能猜测当前版本。结果用延迟×策略矩阵和逐事件匹配审计表呈现。

#### QA-VII：多批次来源比较能否预测候选在后续批次的表现？

对同一来源对齐轨迹并行回放三种规则：首个来源批次、到达顺序诊断规则、来源对齐窗口。窗口长度使用 pilot 参数 3 批只作试运行；正式窗口和阈值须在正式结果前冻结。

**防止自我验证**：候选选择窗口与结果验证窗口必须不重叠。例：用来源批次 `0–2` 可用的反馈形成选择建议；仅用之后 `3–5` 的 held-in 来源对齐分数判断候选是否在后续仍有效。后续窗口标签由预先冻结的质量/退化标准定义，不能复用选择窗口的数据，也不能输入正在做决定的规则。按时间顺序滚动时，各决策样本的未来结果窗口须预先规定，不能把重叠窗口当作独立样本。

**主要指标**：错误保留建议率（建议保留但不重叠的后续结果窗口失败）、错误拒绝建议率（建议保持 stable 但后续窗口成功）、决策延迟批数、候选失败拒绝率、选择窗口和后续窗口的平均/最差 Macro-F1 差。分母分别是有完整未来结果窗口的保留建议数和拒绝建议数；未来窗口不足的 run 标记为不可判定，不填造标签。seed 为配对单位。

**结论边界**：现有回放器能输出三种决策和错配计数，但未实现基于 hindsight 标签的错误保留/错误拒绝汇总，也未执行真实晋升与回退。后两项需新增分析器和在线 runtime 故障实验；离线回放不能替代它们。

### 9.5 三类机制的端到端组合

单项 pilot 验收并完成接口接入后，组合实验采用完整 `2×2×2` 因子设计，而不是只比较“全关”和“全开”：

| 因子 | 关闭 | 开启 |
| --- | --- | --- |
| 候选修改隔离 | 固定 Data System，不运行候选 | 候选独立分支、失败门控和恢复账本 |
| 数据经验治理 | 不保留可执行经验 | 来源/条件记录、暂停、重验与失效处理 |
| 延迟反馈版本选择 | 单批或固定版本决策基线 | 来源版本归因和多批次保留/拒绝策略 |

8 个组合都使用相同完整数据流、初始状态和总预算上限；先用 pilot 估算运行成本，再决定是否能全因子执行。主比较是全开系统对全关 baseline 的系统级效应；因子主效应和交互效应解释每个机制贡献。若预算不足，不能用不平衡且事后挑选的臂冒充完整因子实验，应先删减为预先登记的组合比较并降低结论范围。

**系统主终点**：成功完成批次比例、无数据/反馈/checkpoint 完整性违规的运行比例、故障后恢复成功率；共同报告全程 held-in 预序列 Macro-F1 和总成本。安全违规作为单独计数，不能被平均分抵消。

**结果呈现**：逐 seed 展示 8 臂配对点；用因子效应图报告隔离、经验治理、延迟选择的主效应和交互项；用全流质量与 active version 时间线解释效果发生在哪些批次。在线回退只有在 runtime 真正实现后才能进入该设计。

#### 组合实验的实现与启动门槛

这不是当前可直接启动的实验。开始前按以下顺序补齐工程：

1. 在统一 runtime 中接入 stable/candidate 双分支、经验 policy state、反馈 source/version ID 和版本选择器；所有状态必须进入同一个可原子恢复的 run state。
2. 将经验治理作为每批数据选择步骤，将候选隔离作为候选修改执行边界，将多批来源窗口作为候选晋升规则；关闭某因子时只关闭其机制，不能同时改变模型、数据流、预算或其他因子。
3. 增加配置 schema，显式记录三个二元开关、stream manifest、初始 checkpoint hash、延迟、窗口参数、预算与故障计划；启动时拒绝未知参数及不匹配的 parent/version。
4. 增加逐批集成验收：三项状态都能 checkpoint/恢复；反馈只在到期后可见；source version 对齐；候选失败不污染 stable；所选训练记录和 active version 可重算。
5. 先用确定性 fake-command fixture 跑 8 个组合的 4 批 contract smoke；再用真实模型跑一条 10 批集成 smoke；通过后才冻结完整流、多种子和统计协议。

正式矩阵的每个 seed 需要 8 个组合，每个组合单独输出目录，但共享该 seed 的 manifest、初始 checkpoint、模型训练参数和总预算。先以 pilot 的运行成本确定是否能完成 8 臂；不能删掉不利组合后仍称 factorial design。若实现后仍没有自动 candidate 晋升和 checkpoint 回退，组合实验只能回答集成兼容性与候选观察效果，不能回答在线晋升后的回退稳定性。

本地已具备统一 orchestrator、8 臂配置校验器、集成 fake-command smoke、事件账本恢复、故障注入/回退路径和配对汇总器。真实组合运行仍必须使用真实数据、模型和冻结配置，并单独保存输出目录。

### 9.6 结果工件与可复核性

每批至少需要形成可由脚本复算的记录：

| 文件/字段 | 用途 |
| --- | --- |
| `run_manifest.json` | 数据/流 manifest hash、seed、反馈延迟、模型与代码 revision、实验臂、预算、干预计划。 |
| `batch_metrics.jsonl` | 每批输入数、预测版本、source batch、反馈释放 ID、预序列 confusion matrix、Macro-F1、完成状态和耗时。 |
| `data_selection.jsonl` | 选择前后 record ID 或稳定 hash、各类计数、选择规则与经验状态。仅有数量不足以验证数据选择可复现。 |
| `experience_events.jsonl` | 经验来源、条件、状态前后值、变化检测、暂停/重验、应用与停用原因。 |
| `candidate_events.jsonl` | 提案 hash、父版本、门控结果、故障注入、candidate/stable 状态和成本。 |
| `feedback_events.jsonl` | 来源批次/版本、释放批次、目标版本、匹配结果、是否参与某次决策。 |
| `recovery_events.jsonl` | 中断点、恢复尝试、提交 cursor、前后状态 hash 和逻辑差异。 |

目前部分字段已包含在 `summary.json`、逐批 `batch_history`、candidate audit 和 policy audit 中；以上是结果包目标 schema，不代表所有独立 JSONL 文件已经实现。正式 pilot 前应由汇总程序检查必需字段缺失、实验臂配对键不一致、漏批、重复反馈和 final-test 标志；检查失败时停止生成主结果表。
